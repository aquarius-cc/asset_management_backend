# 审计日志规范

> 适用：资产管理系统后端（Python 3.12+ / Django 6.0 / DRF 3.15+ / PostgreSQL 16）  
> 遵循：`AGENTS.md`（审计红线、信号约束）、`SECURITY.md`（敏感信息保护）  
> 目的：确保所有关键操作可追溯、可审计，满足合规要求。

---

## 1. 核心原则（🔴 红线）

- **审计不可遗漏**：资产核心数据（档案、入库、出库、借用、报废、盘点）的任何变更，必须 **100%** 记录操作人、时间、变更前后快照。
- **非侵入式记录**：通过 Django 信号 + Service 显式调用实现，**禁止**在核心业务代码中混杂审计逻辑。
- **数据不可逆**：审计日志一旦写入，**禁止物理修改或删除**。仅系统管理员可按留存策略执行归档。
- **敏感遮蔽**：所有涉及密码、手机号、身份证、采购价等字段，写入前必须脱敏，禁止日志中泄露明文。

---

## 2. 日志分类与触发条件

| 日志类型       | 代码            | 记录时机                     | 责任模块         |
| ---------- | ------------- | ------------------------ | ------------ |
| **操作日志**   | `OPERATE`     | 用户执行任何增、删、改操作（含 API 调用）  | 全局中间件        |
| **数据变更日志** | `DATA_CHANGE` | 资产核心表的字段发生变更（状态、库存、归属人等） | 信号 + Service |
| **权限日志**   | `PERMISSION`  | 角色/权限分配、回收、修改            | 用户/角色管理模块    |
| **登录日志**   | `LOGIN`       | 登录、登出、登录失败               | 认证模块         |
| **异常日志**   | `EXCEPTION`   | 系统异常（报错、超时、业务校验失败）       | 全局异常处理       |

> 🟡 **资产专属**：`DATA_CHANGE` 日志必须包含变更前后的完整快照（`old_value` / `new_value`）。

---

## 3. 日志字段规范

### 3.1 通用字段（所有日志必含）

| 字段名                | 类型           | 说明                                 | 示例                      |
| ------------------ | ------------ | ---------------------------------- | ----------------------- |
| `log_type`         | VARCHAR(20)  | 日志类型（见上表）                          | `OPERATE`               |
| `operator_id`      | VARCHAR(32)  | 操作人ID；匿名填 `anonymous`，系统填 `system` | `user_10086`            |
| `operator_name`    | VARCHAR(50)  | 操作人姓名（可能脱敏）                        | 张三                      |
| `operator_ip`      | VARCHAR(50)  | 请求IP                               | 192.168.1.100           |
| `operation_time`   | TIMESTAMP    | 操作时间（UTC+8，精确到秒）                   | 2026-05-08 14:30:25     |
| `operation_module` | VARCHAR(50)  | 模块名称（如 `asset`、`user`）             | `asset`                 |
| `operation_desc`   | VARCHAR(200) | 操作描述（可读）                           | 新增资产【办公电脑-001】          |
| `request_url`      | VARCHAR(200) | 接口路径                               | `/api/v1/assets/`       |
| `status`           | SMALLINT     | 1-成功，0-失败                          | 1                       |
| `error_msg`        | TEXT         | 失败时的错误信息                           | 资产编码已存在                 |
| `request_params`   | TEXT         | 请求参数（JSON，已脱敏）                     | `{"asset_name":"办公电脑"}` |

### 3.2 按日志类型的扩展字段

| 日志类型          | 扩展字段                | 类型           | 说明                     |
| ------------- | ------------------- | ------------ | ---------------------- |
| `PERMISSION`  | `permission_type`   | VARCHAR(20)  | ADD / EDIT / DELETE    |
|               | `role_id`           | VARCHAR(32)  | 关联角色ID                 |
| `DATA_CHANGE` | `data_id`           | VARCHAR(32)  | 变更数据主键（如 `asset_code`） |
|               | `old_value`         | TEXT         | 变更前快照（JSON，脱敏）         |
|               | `new_value`         | TEXT         | 变更后快照（JSON，脱敏）         |
| `LOGIN`       | `login_type`        | VARCHAR(20)  | PASSWORD / TOKEN       |
|               | `login_fail_reason` | VARCHAR(100) | 失败原因                   |

## 4. 脱敏规则（强制）

在写入数据库前必须完成脱敏。以下为常见敏感字段的处理方式：

| 字段类型    | 脱敏方法                 | 示例                                     |
| ------- | -------------------- | -------------------------------------- |
| 密码      | 全部替换为 `******`       | `******`                               |
| 手机号     | 保留前3后4，中间 `****`     | `138****1234`                          |
| 邮箱      | 前缀保留2位 + `****@` 域名  | `zh****@example.com`                   |
| 身份证号    | 保留前6后4，中间 `********` | `110101********1234`                   |
| 采购价     | 仅记录是否变更，不记录具体数字      | `{"price":"***","changed":true}` 或直接移除 |
| 合同/维保详情 | 仅记录变更摘要              | `{"warranty":"extended"}`              |

**脱敏实现**：封装在 `core/audit_logger.py` 的工具类中，所有日志写入必须通过该工具。

## 5. 存储与表结构策略

- **主表**：`audit_log`（当前年度），按年分表（如 `audit_log_2026`）。
- **归档表**：`audit_log_<年份>_archive`，存放在只读 PostgreSQL 实例。
- **异常日志**：同时写 PostgreSQL 和 ELK（用于告警）；
- **索引**：`operator_id`、`operation_time`、`log_type` 为联合索引或单一索引，确保查询性能。
- **写入要求**：原子写入，失败重试最多 3 次，并记录重试失败日志。禁止在事务中长时间锁表。

---

## 6. 查询与权限

| 角色                      | 查询范围                                          |
| ----------------------- | --------------------------------------------- |
| `SYS_ADMIN` / `AUDITOR` | 全量日志                                          |
| `OP_ADMIN`              | 仅业务操作日志（`OPERATE` + `DATA_CHANGE`），不可查权限/异常日志 |
| `BUSINESS_USER`         | 无日志查询权限                                       |

查询接口必须支持按 `log_type`、`operator_id`、`time`、`module`、`status` 组合过滤，并强制分页（每页最多 100 条），禁止全表扫描。

---

## 7. 留存与归档

| 日志类型          | 在线留存               | 归档要求             |
| ------------- | ------------------ | ---------------- |
| 操作日志 / 登录日志   | 2 年                | 到期后迁移至归档表        |
| 权限日志 / 数据变更日志 | **永久**             | 每年归档至独立只读实例，禁止删除 |
| 异常日志          | PostgreSQL 1 年，ELK 6 个月 | 到期直接清理（非审计核心）    |

归档操作：每年 1 月执行，执行前必须备份，归档后需抽样验证数据完整性。

---

## 8. 实现规范（对接 AGENTS.md）

- **中间件**：全局记录 `OPERATE` 类型日志，从 `request` 中提取用户、IP、参数并脱敏。
- **信号**：仅使用 `post_save`/`post_delete` 监听 `Asset`、`OutAsset`、`RecycleAsset` 等核心模型，生成 `DATA_CHANGE` 日志（快照对比通过 `pre_save` 缓存旧值——**需在 Service 层显式完成，禁止在信号中直接修改业务数据**）。
- **Service 层**：对于复杂数据变更（如单据状态扭转），在事务中显式调用 `AuditLogger.log_data_change(...)`。
- **工具类**：提供统一接口 `core/audit_logger.py`，负责脱敏、构建日志对象并写入。
- **异常日志**：由全局 `EXCEPTION_HANDLER` 捕获后记录。

**核心代码结构参考（工具类示例）**：

```
python

# core/audit_logger.py

class AuditLogger:
    @staticmethod
    def log_operation(request, module, action_desc, status, error_msg=""):
        # 从request提取信息，脱敏params，写入 OPERATE 日志
        ...
    @staticmethod
    def log_data_change(data_id, old_val, new_val, operator):
        # 脱敏后写入 DATA_CHANGE 日志
```

## 9. 开发自检清单

| 类别     | 检查项                               |
| ------ | --------------------------------- |
| **记录** | ✅ 资产核心变更 100% 生成 `DATA_CHANGE` 日志 |
|        | ✅ 所有写操作 API 调用生成 `OPERATE` 日志     |
|        | ✅ 权限变更、登录行为有对应日志                  |
| **脱敏** | ✅ 密码/手机/身份证/采购价等字段写入前已脱敏          |
| **存储** | ✅ 分表策略已配置，索引已建立                   |
| **查询** | ✅ 日志查询接口权限受控，分页且无全表扫描             |
| **归档** | ✅ 归档脚本就绪，数据完整性验证通过                |
| **合规** | ✅ 不存在删除或修改已生成日志的代码路径              |
| **性能** | ✅ 日志写入异步化或批量写入，不阻塞主业务流程           |
