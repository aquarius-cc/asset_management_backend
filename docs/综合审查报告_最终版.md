## 一、致命问题

### 1.1 多个 ViewSet 的 batch_delete action 权限控制缺失

**问题描述**: `StorageViewSet`、`AssetTypeViewSet`、`ContractViewSet` 的 `batch_delete` action 仅设置了 `permission_classes = [IsAuthenticated]`（或 `[permissions.IsAuthenticated]`），未要求管理员权限。普通认证用户可调用批量删除接口，存在严重的越权风险。

**对比正确做法**: `AssetViewSet`、`OutAssetViewSet`、`RecycleAssetViewSet`、`EmployeeViewSet`、`DepartmentViewSet` 均通过 `get_permissions()` 方法对 `batch_create`/`batch_delete` action 强制要求 `IsAdminUser`。

**具体位置与代码**:

#### (1) StorageViewSet — `apps/assetmanagement/views.py:120-123`
```python
class StorageViewSet(LoggingMixin, ResponseWrapperMixin, ModelViewSet):
    queryset = Storage.objects.all()
    serializer_class = StorageSerializer
    permission_classes = [IsAuthenticated]  # ❌ 未区分 batch_delete
    pagination_class = CustomPageNumberPagination
```
`batch_delete` action 位于 `views.py:200-219`，继承自类级别的 `permission_classes`，未做额外限制。

#### (2) AssetTypeViewSet — `apps/assetmanagement/views.py:222-226`
```python
class AssetTypeViewSet(LoggingMixin, ResponseWrapperMixin, ModelViewSet):
    queryset = AssetType.objects.all()
    serializer_class = AssetTypeSerializer
    pagination_class = CustomPageNumberPagination
    permission_classes = [permissions.IsAuthenticated]  # ❌ 未区分 batch_delete
```
`batch_delete` action 位于 `views.py:286-303`，继承自类级别的 `permission_classes`，未做额外限制。

#### (3) ContractViewSet — `apps/assetmanagement/views.py:306-308`
```python
class ContractViewSet(LoggingMixin, ResponseWrapperMixin, ModelViewSet):
    queryset = Contract.objects.all()
    permission_classes = [permissions.IsAuthenticated]  # ❌ 未区分 batch_delete
```
`batch_delete` action 位于 `views.py:358-377`，继承自类级别的 `permission_classes`，未做额外限制。

**修复方案**:
为上述三个 ViewSet 添加 `get_permissions()` 方法，对 `batch_delete`（以及 `batch_create` 如果存在）强制要求 `IsAdminUser`：

```python
def get_permissions(self) -> list:
    if self.action in ['batch_delete']:
        permission_classes = [permissions.IsAdminUser]
    else:
        permission_classes = [permissions.IsAuthenticated]
    return [permission() for permission in permission_classes]
```

**风险等级**: 高 — 普通用户可批量删除仓库、资产类型、合同等基础数据，可能导致数据灾难性丢失。

## 二、严重问题

### 2.1 usermanagement 批量删除方法未使用 transaction.atomic

**问题描述**: `EmployeeService.batch_delete_employee` 和 `DepartmentService.batch_delete_department` 在逐条删除时，未对单条删除操作包裹 `transaction.atomic`。虽然批量删除整体采用"逐条独立执行、单条失败不影响其他"的策略，但单条删除内部涉及多个数据库操作（查询 + 关联检查 + 删除）时，若中途异常可能导致数据不一致。

**具体位置与代码**:

#### (1) EmployeeService.batch_delete_employee — `apps/usermanagement/services.py:130-198`
```python
@staticmethod
def batch_delete_employee(employee_jobcodes: List[str]) -> Dict[str, Any]:
    # ... MAX_BATCH_SIZE 校验 ...
    for jobcode in employee_jobcodes:
        try:
            employee = EmployeeSelector.get_employee_by_jobcode(jobcode)
            # ... 关联检查 ...
            employee.delete()  # ❌ 无 transaction.atomic 包裹
            success_ids.append(jobcode)
        except Exception:
            # ...
```

#### (2) DepartmentService.batch_delete_department — `apps/usermanagement/services.py:483-550`
```python
@staticmethod
def batch_delete_department(department_codes: List[str]) -> Dict[str, Any]:
    # ... MAX_BATCH_SIZE 校验 ...
    for dept_code in department_codes:
        try:
            department = DepartmentSelector.get_department_by_code(dept_code)
            # ... 关联检查 ...
            department.delete()  # ❌ 无 transaction.atomic 包裹
            success_ids.append(dept_code)
        except Exception:
            # ...
```

**对比正确做法**: `OutAssetService.batch_delete_outasset`（`services.py:868`）和 `RecycleAssetService.batch_delete_recycle_asset`（`services.py:1148`）均在循环内使用 `with transaction.atomic():` 包裹单条删除逻辑。

**修复方案**:
在 `batch_delete_employee` 和 `batch_delete_department` 的循环体内，将关联检查和删除操作包裹在 `with transaction.atomic():` 中：

```python
for jobcode in employee_jobcodes:
    try:
        with transaction.atomic():
            employee = EmployeeSelector.get_employee_by_jobcode(jobcode)
            # ... 关联检查 ...
            employee.delete()
        success_ids.append(jobcode)
    except Exception:
        # ...
```

**风险等级**: 中高 — 单条删除过程中若发生异常（如并发修改、数据库连接中断），可能导致关联检查已通过但删除未完成，留下不一致状态。

## 三、警告

### 3.1 BatchOperationMixin 使用不一致

**问题描述**: 项目中存在统一的批量操作框架 `BatchOperationMixin`（`core/batch_mixins.py`），但部分 Service 的批量方法使用了 Mixin，部分仍使用手写循环，导致代码重复、维护成本增加、异常处理风格不一致。

**已使用 Mixin 的 Service**:
| Service | 方法 | 位置 |
|---------|------|------|
| AssetService | `batch_create_asset` | `services.py:369` |
| ContractService | `batch_delete_contract` | `services.py:1793` |
| StorageService | `batch_delete_storage` | `services.py:1884` |
| AssetTypeService | `batch_delete_asset_type` | `services.py:1968` |

**未使用 Mixin 的 Service**（手写循环）:
| Service | 方法 | 位置 |
|---------|------|------|
| AssetService | `batch_delete_asset` | `services.py:377-475` ❌ 同个类中 create 用 Mixin，delete 不用 |
| OutAssetService | `batch_create_outasset` | `services.py:775-839` |
| OutAssetService | `batch_delete_outasset` | `services.py:841-930` |
| RecycleAssetService | `batch_create_recycle_asset` | `services.py:1062-1121` |
| RecycleAssetService | `batch_delete_recycle_asset` | `services.py:1124-1201` |
| EmployeeService | `batch_create_employee` | `services.py:75-128` |
| EmployeeService | `batch_delete_employee` | `services.py:130-198` |
| DepartmentService | `batch_create_department` | `services.py:428-481` |
| DepartmentService | `batch_delete_department` | `services.py:483-550` |

**修复方案**:
1. **AssetService.batch_delete_asset**: 补充使用 `BatchOperationMixin.batch_delete_execute`，参考 ContractService 的实现模式。
2. **OutAssetService / RecycleAssetService**: 将 `batch_create_*` 和 `batch_delete_*` 重构为使用 `BatchOperationMixin.batch_execute` / `batch_delete_execute`。
3. **EmployeeService / DepartmentService**: 同样重构为使用 Mixin，统一异常处理和返回格式。

**优先级**: 中 — 不影响功能正确性，但增加维护成本和引入不一致 bug 的风险。

### 3.2 ContractViewSet.destroy 异常处理不一致

**问题描述**: `ContractViewSet.destroy`（`views.py:345-356`）捕获异常时使用了 `ValidationError` 和 `NotFoundError`，而不是项目统一定义的 `AppValidationError` 和 `NotFoundError`（来自 `core.exceptions`）。虽然 `core/exceptions.py:103` 定义了 `ValidationError = AppValidationError` 的别名保持向后兼容，但这种混用降低了代码一致性，且 `NotFoundError` 的导入来源不明确（可能来自 `rest_framework.exceptions` 或 `core.exceptions`）。

**具体代码** — `apps/assetmanagement/views.py:345-356`:
```python
def destroy(self, request, *args, **kwargs):
    try:
        contract = self.get_object()
        ContractService.delete_contract(contract.contract_code)
        return success_response(message='删除成功')
    except ValidationError as e:      # ❌ 混用 ValidationError（应为 AppValidationError）
        return error_response(message=str(e), status_code=400)
    except NotFoundError as e:        # ❌ 混用 NotFoundError
        return error_response(message=str(e), status_code=404)
    except Exception as e:
        logging.exception('合同删除失败')
        return error_response(message='删除失败，请稍后重试', status_code=500)
```

**对比正确做法**: `StorageViewSet.destroy`（`views.py:189-198`）统一使用 `AppValidationError`：
```python
except AppValidationError as e:
    return error_response(message=str(e.detail), status_code=400)
```

**修复方案**:
将 `ContractViewSet.destroy` 的异常捕获统一改为 `AppValidationError` 和 `NotFoundError`（明确从 `core.exceptions` 导入），并统一使用 `str(e.detail)` 获取错误信息。

### 3.3 HardDiskSNViewSet 无权限控制

**具体代码** — `apps/assetmanagement/views.py:1689-1714`:

class HardDiskSNViewSet(LoggingMixin, ResponseWrapperMixin, ModelViewSet):

**修复方案**:

2. 重写 `get_permissions()`，对 `batch_save` action 要求 `IsAdminUser`：

## 四、优化建议

### 4.1 统一 ViewSet 权限控制模式

**现状**: 项目中存在两种权限控制模式：
- 类级别 `permission_classes = [...]`（StorageViewSet、AssetTypeViewSet、ContractViewSet、HardDiskSNViewSet）
- 方法级别 `get_permissions()`（AssetViewSet、OutAssetViewSet、RecycleAssetViewSet、EmployeeViewSet、DepartmentViewSet）

**建议**: 所有包含批量操作的 ViewSet 统一使用 `get_permissions()` 模式，明确区分普通操作和批量操作的权限要求，避免遗漏。

### 4.2 BatchOperationMixin 全面推广

**现状**: 约 50% 的批量方法未使用 `BatchOperationMixin`。

**建议**: 制定批量操作编码规范，强制要求所有新增批量方法使用 `BatchOperationMixin`。对存量手写循环的批量方法，安排技术债清理，优先处理 `AssetService.batch_delete_asset`（同个类中已使用 Mixin 的 create 方法，delete 方法也应统一）。

### 4.3 异常处理风格统一

**现状**: 部分视图使用 `str(e)`，部分使用 `str(e.detail)`；部分混用 DRF 原生异常和项目自定义异常。

**建议**: 统一规范：
- 所有视图层捕获项目自定义异常（`AppValidationError`、`NotFoundError`、`BusinessLogicError`）
- 获取错误信息统一使用 `str(e.detail)`
- 禁止直接使用 DRF 的 `ValidationError`（除非在 Serializer 内部）

### 4.4 批量删除操作日志覆盖

**现状**: `AssetService.batch_delete_asset` 在循环内调用了 `AuditLogger.log_asset_delete()`，但 `OutAssetService.batch_delete_outasset`、`RecycleAssetService.batch_delete_recycle_asset`、`ContractService.batch_delete_contract` 等未在批量删除中记录审计日志。

**建议**: 统一批量操作的审计日志记录，确保批量删除的可追溯性。

### 5.3 整体评估

该项目在架构层面已经建立了较好的规范基础：
- 使用 `BatchOperationMixin` 统一批量操作框架
- 使用 `Selector` 模式隔离查询逻辑
- 使用 `Service` 层封装业务逻辑
- 使用 `AppValidationError` 等自定义异常

但在**执行层面**存在以下薄弱环节：
- **权限控制不严谨**: 部分 ViewSet 遗漏了批量操作的权限区分，这是本次审查发现的最严重问题

- **事务意识不足**: usermanagement 模块的批量删除未考虑单条操作的事务完整性

建议将本次审查发现的问题纳入 Sprint 技术债清单，优先处理 P0/P1 级别问题，确保系统安全性和数据一致性。
