# 资产管理系统综合审查报告 —— 批量创建/删除代码专项审查

> 审查日期：2026-06-11
> 审查范围：apps/assetmanagement/ 与 apps/usermanagement/ 的批量操作新增代码
> 审查维度：逻辑错误、安全风险、性能风险、数据一致性、代码质量、兼容性

---

## 一、逻辑错误

### 问题 1-1：OutAsset 批量删除后资产状态恢复不完整

- **问题描述**：`OutAssetService.batch_delete_outasset()` 在删除出库记录后，将资产状态恢复为 `in_store`，但 `asset_storage_code` 被设为 `None`。如果原资产是从 `recycled_pending` 状态出库的，删除后应恢复为 `recycled_pending`，而不是统一恢复为 `in_store`。此外，`asset_applicant_jobcode`、`asset_manager_jobcode`、`asset_using_location` 等出库时设置的字段未被清空。
- **影响范围**：`apps/assetmanagement/services.py` — `OutAssetService.batch_delete_outasset()`
- **严重程度**：高
- **修复建议**：
  1. 使用 `outasset_previous_status` 字段恢复资产原状态（而非硬编码 `in_store`）
  2. 清空 `asset_applicant_jobcode`、`asset_manager_jobcode`、`asset_using_location` 等出库相关字段
  3. 参考 `AssetFSM.cancel_outasset` 的实现逻辑

```python
# 修复示例
previous_status = outasset.outasset_previous_status or 'in_store'
asset.asset_current_status = previous_status
asset.asset_applicant_jobcode = None
asset.asset_manager_jobcode = None
asset.asset_using_location = None
asset.save(update_fields=[
    'asset_current_status', 'asset_applicant_jobcode',
    'asset_manager_jobcode', 'asset_using_location'
])
```

---

### 问题 1-2：RecycleAsset 批量删除后未恢复资产状态

- **问题描述**：`RecycleAssetService.batch_delete_recycle_asset()` 仅执行了回收记录的软删除，但关联资产的状态仍保持 `recycled_pending`，未恢复为 `in_use`（出库状态）或 `in_store`。
- **影响范围**：`apps/assetmanagement/services.py` — `RecycleAssetService.batch_delete_recycle_asset()`
- **严重程度**：高
- **修复建议**：删除回收记录后，需将关联资产状态恢复为删除前的状态（应为 `in_use`，因为回收记录是从出库记录创建的）。需要确认业务规则：删除回收记录是否意味着"撤销回收"，资产应回到在用状态。

---

### 问题 1-3：Employee 批量删除的前置校验遗漏

- **问题描述**：`EmployeeService.batch_delete_employee()` 检查了员工作为申请人和保管人的 `OutAsset` 关联，但未检查：
  1. 员工是否作为 `asset_entry_person_jobcode`（入库人）关联资产
  2. 员工是否作为 `asset_applicant_jobcode` 或 `asset_manager_jobcode` 直接关联 `Asset` 表
  3. 员工是否作为 `approver` 关联 `DamagedAsset` 审批记录
- **影响范围**：`apps/usermanagement/services.py` — `EmployeeService.batch_delete_employee()`
- **严重程度**：中
- **修复建议**：补充上述关联检查，或统一使用数据库级外键约束（当前 `on_delete` 为 `DO_NOTHING`/`SET_NULL`，不会阻止删除）。

---

### 问题 1-4：Department 批量删除未检查关联资产

- **问题描述**：`DepartmentService.batch_delete_department()` 检查了子部门和员工，但未检查该部门是否关联资产（`Asset.asset_department_code`）。
- **影响范围**：`apps/usermanagement/services.py` — `DepartmentService.batch_delete_department()`
- **严重程度**：中
- **修复建议**：补充检查 `Asset.objects.filter(asset_department_code=department, is_deleted=False).exists()`。

---

### 问题 1-5：批量创建时 `asset_name` 重复校验逻辑有误

- **问题描述**：`AssetBatchCreateSerializer.validate_items()` 仅校验提交列表内的 `asset_name` 重复，但未校验与数据库已有记录的重复。如果数据库中已存在同名资产，批量创建时会因数据库唯一约束失败，但错误信息可能不友好。
- **影响范围**：`apps/assetmanagement/serializers.py` — `AssetBatchCreateSerializer`
- **严重程度**：低
- **修复建议**：明确 `asset_name` 是否为业务唯一字段。如果是，需在序列化器层增加数据库级重复检查；如果不是，应移除列表内重复校验或调整错误码。

## 二、安全风险

### 问题 2-1：批量操作接口缺乏权限控制

- **问题描述**：`AssetViewSet`、`OutAssetViewSet`、`RecycleAssetViewSet` 的 `batch_create` 和 `batch_delete` action 未单独配置权限类，继承了 ViewSet 级别的 `permission_classes = [IsAuthenticated]`。这意味着任何认证用户都可以执行批量创建/删除，而不仅是管理员。
- **影响范围**：`apps/assetmanagement/views.py` — 所有批量操作 ViewSet action
- **严重程度**：高
- **修复建议**：为批量操作 action 增加管理员权限校验：

```python
@action(detail=False, methods=['post'], url_path='batch-delete', 
        permission_classes=[permissions.IsAdminUser])
def batch_delete(self, request):
    ...
```

---

### 问题 2-2：UserManagement 批量操作权限与单条操作不一致

- **问题描述**：`DepartmentViewSet` 和 `EmployeeViewSet` 的 `get_permissions()` 方法中，`batch_create` 和 `batch_delete` action 未被包含在管理员权限列表中。当前逻辑仅对 `create`, `update`, `partial_update`, `destroy` 要求 `IsAdminUser`，`batch_create`/`batch_delete` 作为自定义 action 默认使用 `IsAuthenticated`。
- **影响范围**：`apps/usermanagement/views.py` — `DepartmentViewSet`, `EmployeeViewSet`
- **严重程度**：高
- **修复建议**：在 `get_permissions()` 中明确包含批量操作 action：

```python
if self.action in ['create', 'update', 'partial_update', 'destroy', 
                   'batch_create', 'batch_delete']:
    permission_classes = [permissions.IsAdminUser]
```

---

### 问题 2-3：批量删除缺乏操作审计日志

- **问题描述**：`batch_delete_outasset()` 和 `batch_delete_recycle_asset()` 未记录审计日志（AuditLogger），与单条删除的审计规范不一致。`usermanagement` 的批量删除也完全未记录日志。
- **影响范围**：所有批量删除 Service 方法
- **严重程度**：中
- **修复建议**：在批量删除的成功分支中调用对应的 AuditLogger 方法，或在循环中逐条记录。

---

### 问题 2-4：批量操作无速率限制

- **问题描述**：所有批量操作接口允许单次处理最多 100 条记录，但缺乏接口级速率限制（如每用户每分钟最多调用次数），存在被恶意滥用的风险。
- **影响范围**：所有批量操作 View
- **严重程度**：低
- **修复建议**：在 DRF 配置中增加 `DEFAULT_THROTTLE_CLASSES`，为批量操作接口配置独立节流策略。

---

## 三、性能风险

### 问题 3-1：批量删除存在 N+1 查询

- **问题描述**：所有批量删除方法在循环中逐条查询关联数据。例如 `batch_delete_asset()` 中每条记录都执行 `AssetSelector.get_asset_by_code()`，然后分别查询 `OutAsset` 和 `DamagedAsset` 的关联存在性。
- **影响范围**：所有批量删除 Service 方法
- **严重程度**：中
- **修复建议**：使用 `prefetch_related` 或 `in` 查询批量获取关联数据：

```python
# 优化示例
assets = Asset.objects.filter(asset_code__in=asset_codes)
outasset_codes = set(OutAsset.objects.filter(
    outasset_code__asset_code__in=asset_codes, 
    is_deleted=False
).values_list('outasset_code__asset_code', flat=True))
```

---

### 问题 3-2：批量创建未使用 `bulk_create`

- **问题描述**：`batch_create_asset()` 复用单条 `create_asset()`，逐条执行 `Asset.objects.create()` 和 `AuditLogger.log_asset_create()`。对于大批量场景，这会产生大量 INSERT 语句。
- **影响范围**：`apps/assetmanagement/services.py` — `AssetService.batch_create_asset()`
- **严重程度**：低
- **修复建议**：对于纯批量场景（无需逐条审计日志），考虑使用 Django `bulk_create()` 优化。当前逐条模式适合需要详细错误报告的场景，属于设计权衡，但应在文档中说明性能影响。

---

### 问题 3-3：序列化器重复查询数据库

- **问题描述**：`DepartmentTreeSerializer.get_children()` 递归序列化时，每条子部门记录都会触发新的数据库查询。在部门层级较深时，会产生大量查询。
- **影响范围**：`apps/usermanagement/serializers.py` — `DepartmentTreeSerializer`
- **严重程度**：中
- **修复建议**：使用 `prefetch_related` 预加载子部门，或在 Selector 层构建树形结构时一次性查询所有部门。

---

## 四、数据一致性

### 问题 4-1：批量操作部分成功导致的数据不一致

- **问题描述**：所有批量操作采用"逐条独立执行"模式，单条失败不影响其他记录。这虽然提高了容错性，但可能导致业务上的部分成功状态。例如：批量出库 10 条资产，成功 5 条失败 5 条，此时 5 条资产已变为 `in_use`，5 条仍为 `in_store`，业务上可能需要人工介入处理失败记录。
- **影响范围**：所有批量操作 Service 方法
- **严重程度**：中
- **修复建议**：
  1. 在 API 文档中明确说明部分成功行为
  2. 提供"批量回滚"或"批量重试"接口
  3. 对于强一致性要求的场景，提供事务性批量操作选项（全部成功或全部失败）

---

### 问题 4-2：OutAsset 批量删除时资产状态与出库记录不一致

- **问题描述**：`batch_delete_outasset()` 中，先执行 `outasset.delete()`（软删除），再修改 `asset` 状态。如果资产状态保存失败，会出现"出库记录已删除但资产仍显示在用"的不一致状态。且该操作未使用 `@transaction.atomic`。
- **影响范围**：`apps/assetmanagement/services.py` — `OutAssetService.batch_delete_outasset()`
- **严重程度**：高
- **修复建议**：为单条删除逻辑添加 `@transaction.atomic`，确保出库记录删除和资产状态恢复在同一个事务中。

---

### 问题 4-3：Employee/Department 硬删除与 Asset 软删除混用

- **问题描述**：`EmployeeService.batch_delete_employee()` 和 `DepartmentService.batch_delete_department()` 使用 `employee.delete()` 和 `department.delete()`，但 Employee 和 Department 模型的 `delete()` 方法是软删除（设置 `is_deleted=True`）。然而，这些模型不继承 `BaseModel`，其软删除实现与资产管理模块的 `BaseModel` 软删除机制不同，可能导致跨模块数据一致性理解混乱。
- **影响范围**：`apps/usermanagement/services.py`
- **严重程度**：低
- **修复建议**：统一文档说明，明确各模块的删除策略。考虑让 Employee/Department 也继承 BaseModel 以统一软删除行为。

## 五、代码质量

### 问题 5-1：错误码映射函数重复且脆弱

- **问题描述**：每个 Service 模块都有独立的 `_map_*_error_code()` 函数，通过字符串匹配（如 `"已存在" in msg`）映射错误码。这种方式：
  1. 容易因错误消息微调而失效
  2. 错误码定义分散，难以维护
  3. 不同模块的同类错误码命名不一致
- **影响范围**：所有 Service 文件
- **严重程度**：中
- **修复建议**：
  1. 在 `core/exceptions.py` 中定义统一的错误码枚举
  2. 抛异常时直接携带错误码，而非在映射函数中反向解析

```python
# 建议示例
class AppValidationError(Exception):
    def __init__(self, detail, code="VALIDATION_ERROR"):
        self.detail = detail
        self.code = code
```

---

### 问题 5-2：批量大小限制重复定义

- **问题描述**：`MAX_BATCH_SIZE = 100` 在序列化器和 Service 中重复定义。例如 `AssetBatchCreateSerializer` 和 `AssetService.batch_create_asset()` 各自定义了相同的常量。
- **影响范围**：所有批量操作文件
- **严重程度**：低
- **修复建议**：将 `MAX_BATCH_SIZE` 提取到 `core/constants.py` 中作为全局常量。

---

### 问题 5-3：类型注解不完整

- **问题描述**：部分批量方法的返回类型标注为 `Dict[str, Any]`，但内部结构实际上是固定的。应使用 `TypedDict` 提供更精确的类型注解。
- **影响范围**：所有批量操作 Service 方法
- **严重程度**：低
- **修复建议**：定义 `BatchResult` TypedDict：

```python
from typing import TypedDict, List, Dict, Any

class BatchResult(TypedDict):
    total: int
    success_count: int
    fail_count: int
    success_items: List[Any]
    fail_items: List[Dict[str, Any]]
```

---

### 问题 5-4：`import copy` 位置不一致

- **问题描述**：`OutAssetService.batch_create_outasset()` 和 `RecycleAssetService.batch_create_recycle_asset()` 在方法内部 `import copy`，而 `EmployeeService` 和 `DepartmentService` 在文件顶部导入。风格不统一。
- **影响范围**：`apps/assetmanagement/services.py`, `apps/usermanagement/services.py`
- **严重程度**：低
- **修复建议**：统一在文件顶部导入标准库模块。

---

### 问题 5-5：异常处理过于宽泛

- **问题描述**：所有批量操作的 `except Exception` 捕获过于宽泛，可能吞掉本应暴露的编程错误（如 `AttributeError`、`KeyError`），导致调试困难。
- **影响范围**：所有批量操作 Service 方法
- **严重程度**：中
- **修复建议**：
  1. 明确捕获预期的业务异常（`AppValidationError`、`ValidationError`）
  2. 对 `DatabaseError` 单独处理
  3. 保留原始异常信息到日志，仅向用户返回友好消息

```python
except Exception as e:
    logger.exception(f"批量操作失败: {e}")  # 记录完整堆栈
    fail_items.append({
        "error_code": "INTERNAL_ERROR",
        "error_message": "服务器内部错误，请稍后重试"
    })
```

## 六、与现有代码的兼容性

### 问题 6-1：URL 路由命名潜在冲突

- **问题描述**：`batch_create` 和 `batch_delete` action 的 `url_path` 分别为 `batch-create` 和 `batch-delete`。如果未来 DRF 默认路由或其他 action 也使用类似命名，可能产生冲突。
- **影响范围**：所有 ViewSet 的批量操作 action
- **严重程度**：低
- **修复建议**：当前命名清晰，暂无冲突。建议在 `urls.py` 中显式定义批量操作路由，避免依赖 DRF 自动路由生成。

---

### 问题 6-2：序列化器命名风格一致

- **问题描述**：批量序列化器命名统一为 `XxxBatchCreateSerializer` / `XxxBatchDeleteSerializer`，与现有 `XxxCreateSerializer` / `XxxUpdateSerializer` 风格一致，命名规范良好。
- **影响范围**：所有序列化器文件
- **严重程度**：无问题
- **修复建议**：保持当前命名风格。

---

### 问题 6-3：响应格式与现有接口一致

- **问题描述**：批量操作返回的响应格式（`total`, `success_count`, `fail_count`, `success_items`/`success_ids`, `fail_items`）在各模块间保持一致，与现有 `success_response`/`error_response` 工具函数兼容。
- **影响范围**：所有视图文件
- **严重程度**：无问题
- **修复建议**：保持当前响应格式。

## 七、整体评估

### 7.1 总体评价

批量操作代码整体结构清晰，采用了统一的"逐条独立执行、返回详细结果"模式，符合容错性设计要求。序列化器校验、Service 业务逻辑、View 响应格式三层分离良好，与现有架构风格一致。

### 7.2 主要风险点

| 优先级 | 风险点 | 说明 |
|--------|--------|------|
| P0 | 权限控制缺失 | 批量操作接口未限制管理员权限，普通用户可执行批量删除 |
| P0 | OutAsset 删除状态恢复错误 | 硬编码恢复为 `in_store`，未考虑 `recycled_pending` 场景 |
| P1 | RecycleAsset 删除未恢复资产状态 | 删除回收记录后资产状态未回滚 |
| P1 | 数据一致性风险 | 批量删除出库记录时无事务保护 |
| P2 | 错误码映射脆弱 | 字符串匹配方式易失效，建议重构 |
| P2 | N+1 查询性能问题 | 批量删除可优化为批量查询 |

### 7.3 优先修复建议

1. **立即修复（P0）**：
   - 为所有批量操作接口添加 `IsAdminUser` 权限控制
   - 修复 `OutAssetService.batch_delete_outasset()` 的资产状态恢复逻辑

2. **本周修复（P1）**：
   - 修复 `RecycleAssetService.batch_delete_recycle_asset()` 的资产状态回滚
   - 为批量删除操作添加事务保护
   - 补充 Employee/Department 删除的前置关联检查

3. **后续优化（P2）**：
   - 统一错误码定义，重构 `_map_*_error_code()` 函数
   - 优化批量删除的 N+1 查询问题
   - 提取 `MAX_BATCH_SIZE` 为全局常量
   - 完善批量操作的审计日志记录
