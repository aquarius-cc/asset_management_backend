## 一、致命问题

### 1. 权限控制缺失 - DepartmentViewSet
- **文件**: `apps/usermanagement/views.py`
- **行号**: 第 53 行
- **问题描述**: `DepartmentViewSet.get_permissions()` 仅对 `['create', 'update', 'partial_update', 'destroy']` 检查 `IsAdminUser` 权限，但遗漏了自定义批量操作 action：`batch_create`、`batch_delete`、`sort`。这意味着普通认证用户可通过这些接口批量创建/删除部门或修改排序，存在严重的越权风险。
- **当前代码**:
  ```python
  if self.action in ['create', 'update', 'partial_update', 'destroy']:
      permission_classes = [permissions.IsAdminUser]
  ```
- **修复建议**:
  ```python
  if self.action in ['create', 'update', 'partial_update', 'destroy',
                      'batch_create', 'batch_delete', 'sort']:
      permission_classes = [permissions.IsAdminUser]
  ```

### 2. 权限控制缺失 - EmployeeViewSet
- **文件**: `apps/usermanagement/views.py`
- **行号**: 第 617 行
- **问题描述**: `EmployeeViewSet.get_permissions()` 同样遗漏了自定义批量操作 action：`batch_create`、`batch_delete`。更严重的是，`batch_sort` 方法（第 860 行）直接使用了 `permission_classes=[permissions.IsAuthenticated]`，而非 `IsAdminUser`，导致普通用户可批量修改员工排序。
- **当前代码**:
  ```python
  # get_permissions 中
  if self.action in ['create', 'update', 'partial_update', 'destroy']:
      permission_classes = [permissions.IsAdminUser]

  # batch_sort 装饰器
  @action(..., permission_classes=[permissions.IsAuthenticated])
  def batch_sort(self, request):
  ```
- **修复建议**:
  1. 将 `batch_create`、`batch_delete`、`batch_sort` 加入 `get_permissions()` 的权限检查列表
  2. 移除 `batch_sort` 上的 `permission_classes` 参数，统一由 `get_permissions()` 控制

### 3. batch_delete_employee 使用硬删除而非软删除
- **文件**: `apps/usermanagement/services.py`
- **行号**: 第 182 行
- **问题描述**: `EmployeeService.batch_delete_employee()` 中直接调用 `employee.delete()`（第 182 行）。虽然 `Employee` 模型已定义了软删除的 `delete()` 方法（将 `is_deleted` 设为 True），但批量删除逻辑中使用了 `EmployeeSelector.get_employee_by_jobcode(jobcode)` 获取员工。需要确认 Selector 是否过滤了 `is_deleted=True` 的记录。如果 Selector 未过滤，则对已软删除的员工再次调用 `delete()` 会导致 `is_deleted` 已经是 True 的情况下再次保存，虽然不会物理删除，但逻辑上存在重复删除的问题。更关键的是，批量删除返回的成功列表可能包含已经软删除的记录，造成数据不一致。
- **当前代码**:
  ```python
  employee.delete()  # 第182行
  success_ids.append(jobcode)
  ```
- **修复建议**:
  1. 在删除前检查 `employee.is_deleted` 状态，避免重复删除
  2. 确保 `EmployeeSelector.get_employee_by_jobcode()` 过滤 `is_deleted=False`
  3. 明确使用软删除，并在删除前校验关联数据（如出库记录）

### 4. batch_delete_department 使用硬删除
- **文件**: `apps/usermanagement/services.py`
- **行号**: 第 527 行
- **问题描述**: `DepartmentService.batch_delete_department()` 中直接调用 `department.delete()`（第 527 行）。`Department` 模型同样已实现软删除 `delete()` 方法（设置 `is_deleted=True`），但批量删除前未检查 `is_deleted` 状态，可能导致重复操作。此外，与 Asset 模块的批量删除（明确软删除并恢复关联状态）相比，部门删除后未处理关联员工的部门归属问题。
- **当前代码**:
  ```python
  department.delete()  # 第527行
  success_ids.append(dept_code)
  ```
- **修复建议**:
  1. 删除前检查 `department.is_deleted` 状态
  2. 考虑关联员工的处理策略（如设为默认部门或阻止删除）

## 二、严重问题

### 5. HardDiskSNService.batch_save() 缺少 MAX_BATCH_SIZE 检查
- **文件**: `apps/assetmanagement/services.py`
- **行号**: 第 1893 行
- **问题描述**: `HardDiskSNService.batch_save()` 接收 `disks` 数组并直接遍历处理，但未对 `len(disks)` 进行上限校验。如果前端传入超大数组（如数千条），可能导致数据库连接超时、内存溢出或事务锁持有时间过长，影响系统稳定性。
- **当前代码**:
  ```python
  def batch_save(validated_data: Dict[str, Any]) -> Dict[str, Any]:
      asset_code_str = validated_data["asset_code"]
      disks = validated_data["disks"]  # 无长度校验
  ```
- **修复建议**:
  ```python
  MAX_BATCH_SIZE = 100
  if len(disks) > MAX_BATCH_SIZE:
      raise AppValidationError(
          detail=f"单次批量保存不能超过 {MAX_BATCH_SIZE} 条",
          error_code="BATCH_SIZE_EXCEEDED"
      )
  ```

### 6. DepartmentService.batch_update_sort_order() 缺少 MAX_BATCH_SIZE 检查
- **文件**: `apps/usermanagement/services.py`
- **行号**: 第 391 行
- **问题描述**: `DepartmentService.batch_update_sort_order(items)` 直接遍历 `items` 列表并逐条执行 `update()`，未对 `items` 长度进行上限校验。虽然 `update()` 是轻量级操作，但大量记录仍可能导致性能问题和数据库压力。
- **当前代码**:
  ```python
  def batch_update_sort_order(items: List[Dict[str, Any]]) -> int:
      updated_count = 0
      for item in items:  # 无长度校验
  ```
- **修复建议**:
  ```python
  MAX_BATCH_SIZE = 100
  if len(items) > MAX_BATCH_SIZE:
      raise ValidationError(
          detail=f"单次批量排序不能超过 {MAX_BATCH_SIZE} 条",
          error_code="BATCH_SIZE_EXCEEDED"
      )
  ```

### 7. usermanagement 的批量方法未使用 transaction.atomic 包裹单条操作
- **文件**: `apps/usermanagement/services.py`
- **行号**: 第 75-128 行（batch_create_employee）、第 130-198 行（batch_delete_employee）、第 420-474 行（batch_create_department）、第 476-543 行（batch_delete_department）
- **问题描述**: 所有 usermanagement 的批量方法（`batch_create_employee`、`batch_delete_employee`、`batch_create_department`、`batch_delete_department`）在循环内部调用单条 Service 方法时，单条方法有 `@transaction.atomic`，但批量方法本身没有在最外层包裹事务。这意味着：
  1. 单条成功即提交，无法整体回滚
  2. 与 assetmanagement 模块的批量方法（如 `batch_delete_outasset`、`batch_delete_recycle_asset` 在循环内显式使用 `with transaction.atomic()`）不一致
- **当前代码**:
  ```python
  def batch_create_employee(employee_data_list):
      # 无外层事务
      for idx, employee_data in enumerate(employee_data_list):
          try:
              result = EmployeeService.create_employee(...)  # 内部有 @transaction.atomic
  ```
- **修复建议**:
  由于批量方法是"逐条独立执行，单条失败不影响其他"的设计，不需要整体事务包裹。但应在文档中明确说明此设计意图。如果要求原子性，应提供可选参数或单独的原子批量方法。

## 三、警告

### 8. OutAsset/RecycleAsset 批量创建方法使用局部 import copy
- **文件**: `apps/assetmanagement/services.py`
- **行号**: 第 834 行（OutAssetService.batch_create_outasset）、第 1117 行（RecycleAssetService.batch_create_recycle_asset）
- **问题描述**: 两个方法在函数内部使用 `import copy` 而非文件顶部的统一导入。虽然功能正确，但违反了 Python 代码规范（PEP 8），增加了运行时开销（每次调用都执行 import），且与文件顶部已有的 `import copy` 模式不一致（usermanagement/services.py 已在顶部导入）。
- **当前代码**:
  ```python
  def batch_create_outasset(...):
      import copy  # 第834行
      ...

  def batch_create_recycle_asset(...):
      import copy  # 第1117行
      ...
  ```
- **修复建议**:
  将 `import copy` 移至文件顶部（第 18 行附近），删除函数内的局部导入。

### 9. MAX_BATCH_SIZE 重复定义
- **文件**: `apps/usermanagement/services.py`、`apps/assetmanagement/services.py`、`apps/usermanagement/serializers.py`、`apps/assetmanagement/serializers.py`
- **问题描述**: `MAX_BATCH_SIZE = 100` 在多个 Service 和 Serializer 中重复定义，违反了 DRY 原则。如果业务需要调整批量大小上限，需要修改多处代码，容易遗漏。
- **修复建议**:
  将 `MAX_BATCH_SIZE` 提取到 `core/constants.py` 中作为全局常量：
  ```python
  # core/constants.py
  MAX_BATCH_SIZE: int = 100
  ```
  各模块统一导入使用。

### 10. 批量删除部门未处理 is_deleted 过滤
- **文件**: `apps/usermanagement/services.py`
- **行号**: 第 498-527 行
- **问题描述**: `batch_delete_department` 中通过 `DepartmentSelector.get_department_by_code(dept_code)` 获取部门，但未确认 Selector 是否过滤了 `is_deleted=True` 的记录。如果 Selector 未过滤，可能导致对已删除部门重复执行删除操作。
- **修复建议**:
  确认 `DepartmentSelector.get_department_by_code()` 的实现，确保添加 `is_deleted=False` 过滤条件，或在 Service 层增加校验：
  ```python
  if department.is_deleted:
      fail_items.append({..."error_code": "ALREADY_DELETED"...})
      continue
  ```

## 四、优化建议

### 11. 统一批量操作的权限控制模式
- **问题描述**: 当前权限控制分散在 `get_permissions()` 和 `@action(permission_classes=...)` 两个地方，容易遗漏。建议统一使用 `get_permissions()` 方法管理所有权限，避免在 `@action` 上单独指定。
- **涉及文件**: `apps/usermanagement/views.py`

### 12. 统一批量删除的软删除模式
- **问题描述**: Asset 模块的批量删除明确使用软删除（`outasset.delete()` 调用 BaseModel 的软删除），并在删除后恢复关联资产状态。usermanagement 模块虽然模型有软删除能力，但批量删除逻辑未明确体现软删除语义，且未处理关联数据。
- **建议**: 统一所有模块的批量删除行为：
  1. 明确使用软删除
  2. 删除前检查 `is_deleted` 状态
  3. 删除后处理关联数据（或阻止删除）

### 13. 补充 HardDiskSNService.batch_save 的关联资产更新
- **文件**: `apps/assetmanagement/services.py`
- **行号**: 第 1893-1968 行
- **问题描述**: `batch_save` 方法在保存硬盘序列号后，返回结果中包含 `harddisk_number`，但未实际更新关联 `Asset` 对象的 `harddisk_number` 字段。如果资产表的硬盘数量字段与硬盘序列号记录不一致，会导致数据不一致。
- **当前代码**:
  ```python
  return {
      "created": created_count,
      "updated": updated_count,
      "total": len(disks),
      "asset_code": asset_code_str,
      "harddisk_number": len(disks),  # 仅返回，未更新 Asset
  }
  ```
- **修复建议**:
  在事务中同步更新关联资产的硬盘数量：
  ```python
  asset.harddisk_number = len(disks)
  asset.save(update_fields=['harddisk_number'])
  ```

### 14. 统一 transaction.atomic 的使用模式
- **问题描述**: assetmanagement 的批量删除方法在循环内部使用 `with transaction.atomic()` 包裹单条操作，而 usermanagement 的批量方法依赖单条方法的 `@transaction.atomic` 装饰器。两种模式功能相同但风格不一致。
- **建议**: 统一使用 `with transaction.atomic()` 模式，因为它在循环内部更明确，且便于在事务内执行多条关联操作。
