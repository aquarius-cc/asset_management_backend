# 资产业务流程说明书

> 适用：资产管理系统后端（Python 3.12+ / Django 6.0 / DRF 3.15+ / MySQL 8.0）  
> 遵循：`AGENTS.md` 红线（状态流转、事务、审计）、`API_STANDARDS.md`、`权限矩阵表.md`  
> 用途：业务开发、测试用例设计、状态机实现的核心依据。所有流程变更必须同步更新本文档。

---

## 1. 系统定位与核心业务域

资产管理系统覆盖企业资产的入库、领用、外借、归还、报废、盘点等全生命周期管理，支撑合规审计与成本核算。核心业务域如下：

| 业务域      | 功能概述                             | 关键模型（表）                                                           |
| -------- | -------------------------------- | ----------------------------------------------------------------- |
| 资产基础信息管理 | 资产分类、仓库、合同、用户/部门维护               | `AssetType`, `Storage`, `Contract`, `User`                        |
| 资产生命周期管理 | 新增 → 入库 → 领用/外借 → 回收 → 待报废 → 已报废 | `Asset`, `OutAsset`, `RecycleAsset`, `DamagedAsset`, `WasteAsset` |
| 资产盘点     | 定期盘点、差异核对、报告生成                   | 后续扩展                                                              |
| 报表管理     | 台账、领用/报废统计                       | 后续扩展                                                              |

## 2. 资产状态机（🔴 最高约束）

所有资产状态流转必须严格遵循以下状态图，**禁止跨状态或逆流程操作**。状态变更必须包裹事务，并通过前置校验（在 `Serializer` 或 `Service` 中）。

```
                    ┌──────────────┐
                    │  新增资产     │ (in_store)
                    └──────┬───────┘
                           │ 出库（领用/外借）            回收(is_broken)
                           ▼                              ▼
                    ┌──────────────┐              ┌──────────────┐
                    │  在用资产     │ (in_use)      │  已损坏       │ (broken)
                    └──┬───┬───┬───┘              └──────┬───────┘
                       │   │   │ 回收                     │ 提交报废申请
                       │   │   │ 回收(is_lost)            ▼
                       │   │   ▼               ┌──────────────┐
                       │   │ ┌────────────┐    │  待报废       │ (damaged)
                       │   │ │ 已遗失     │    └──┬───────┬───┘
                       │   │ │ (lost)     │       │       │ 审批拒绝→broken/lost
                       │   │ └──┬────┬────┘       │       │
                       │   │    │    │ 找回→in_store│  审批拒绝(按original_status回退)
                       │   │    │    ▼            │
                       │   │    │ ┌──────────┐   │
                       │   │    │ │ 找回记录  │   │
                       │   │    │ │(found)   │   │
                       │   │    │ └──────────┘   │
                       │   │    ▼                ▼
                       │   │ ┌──────────────┐ 审批通过
                       │   │ │ 已回收待发放   │ (recycled_pending)
                       │   │ └──┬───────┬───┘
                       │   │    │       │ 重新发放 → in_use
                       │   │    │       │
                       │   │    ▼       ▼
                       │   └─→ 提交报废申请 → damaged
                       └─────────────→ damaged (直接提交报废)
                                      ▼
                               ┌──────────────┐
                               │  已报废       │ (scrapped) [终态]
                               └──────────────┘
```

**完整状态流转规则**（`AssetFSM._TRANSITIONS`）：

| 当前状态 | 允许的目标状态 | 触发操作 |
|---------|-------------|---------|
| `in_store` | `in_use` | 出库（领用/外借） |
| `in_store` | `broken` | 回收（is_broken=True） |
| `in_store` | `lost` | 回收（is_lost=True） |
| `in_use` | `recycled_pending` | 回收（正常） |
| `in_use` | `broken` | 回收（is_broken=True） |
| `in_use` | `lost` | 回收（is_lost=True） |
| `recycled_pending` | `in_use` | 重新出库（再次发放） |
| `recycled_pending` | `damaged` | 提交报废申请 |
| `broken` | `damaged` | 提交报废申请 |
| `lost` | `damaged` | 提交报废申请 |
| `lost` | `in_store` | 找回入库（通过 FoundAsset） |
| `damaged` | `scrapped` | 审批通过 |
| `damaged` | `broken` | 审批拒绝（original_status=broken） |
| `damaged` | `lost` | 审批拒绝（original_status=lost） |
| `damaged` | `recycled_pending` | 审批拒绝（original_status 其他） |
| `scrapped` | *(无)* | 终态，不可转出 |

**状态值清单**（`asset_current_status`）：

| 状态码 | 中文名 | 说明 | 是否终态 |
|-------|-------|------|---------|
| `in_store` | 在库 | 资产在仓库中，未分配使用 | 否 |
| `in_use` | 在用 | 资产已被领用/出库，正在使用中 | 否 |
| `recycled_pending` | 已回收待发放 | 资产已回收，等待下次分配 | 否 |
| `broken` | 已损坏 | 资产已标记为损坏，等待报废审批 | 否 |
| `lost` | 已遗失 | 资产已标记为遗失，等待找回或报废 | 否 |
| `damaged` | 待报废 | 资产损坏/遗失，等待报废审批 | 否 |
| `scrapped` | 已报废 | 审批通过，资产报废 | **是（不可逆）** |

> 🟡 实现要求：状态码定义在 `Asset` 模型的 `ASSET_STATUS_CHOICES` 常量中，Service 层变更状态前必须校验状态流转合法性。

## 3. 核心业务流程详述

### 流程 1：资产入库（新增 → 入库）

**参与角色**：普通用户（提交申请）、运营管理员（审核/入库）

| 步骤  | 操作         | 角色    | 接口/服务                              | 数据库变更                       | 触发条件/校验                         |
| --- | ---------- | ----- | ---------------------------------- | --------------------------- | ------------------------------- |
| 1   | 填写资产信息并提交  | 普通用户  | `POST /api/v1/assets/`             | `asset` 表创建记录，状态 `in_store` | 必填字段校验（`AssetCreateSerializer`） |
| 2   | 系统自动生成资产编码 | 系统    | `AssetCodeGenerator`               | `asset_code` 事务内生成          | 编码全局唯一，不可修改                     |
| 3   | 入库确认（可选）   | 运营管理员 | `PUT /api/v1/assets/{asset_code}/` | 更新仓库/位置信息                   | 资产状态必须为 `in_store`              |

**⚠️ 重要：`asset_purchase_number` 字段行为**

> 传入 `asset_purchase_number=N` 时，系统会创建 **N 条独立的资产记录**，每条记录生成唯一的 `asset_code`（格式：`ASSET-{category}-{type_code}-{YYYYMMDD}-{random}-{seq}`）。
>
> **示例**：`asset_purchase_number=3` 会创建 3 条资产，编码分别为 `...-0001`、`...-0002`、`...-0003`。

**异常处理**：

| 异常场景              | 处理方式                     |
| ----------------- | ------------------------ |
| 必填字段缺失/格式错误       | 返回 400，`Serializer` 校验失败 |
| 资产编码重复            | 数据库唯一约束，返回 400           |
| 高价值资产（≥5000元）缺少合同 | 业务校验失败，返回 400            |

---

### 流程 2：资产出库（领用/外借）

**参与角色**：申请人、审批人（运营管理员）

| 步骤  | 操作     | 角色   | 接口/服务                      | 数据库变更                                                 | 触发条件/校验                    |
| --- | ------ | ---- | -------------------------- | ----------------------------------------------------- | -------------------------- |
| 1   | 提交出库申请 | 普通用户 | `POST /api/v1/out-assets/` | `out_asset` 表创建，资产状态 `in_use`                           | 资产生效状态必须为 `in_store` 或 `recycled_pending`，非在库拒绝 |
| 2   | 资产状态变更 | 系统自动 | `OutAssetService.create()` | `asset` 表更新：`status→in_use`, `asset_manager`, `asset_using_location` 更新 | 包裹事务，同步写审计日志               |
| 3   | 出库记录生成 | 系统自动 | 服务层调用                 | `out_asset` 记录唯一 `recordcode`（`OUT` 前缀）               | 事务内生成，幂等性保证                |

**领用与外借区别**：仅 `outasset_type` 字段区分（`receive` / `borrow`），外借需填写预计归还日期。

**异常处理**：

| 异常场景   | 处理方式                                             |
| ------ | ------------------------------------------------ |
| 资产已被领用 | 前置校验 `asset_current_status != 'in_store'`，返回 400 |
| 审批超时   | 系统定时任务推送提醒，不自动拒绝                                 |

---

### 流程 3：资产回收（归还）

**参与角色**：归还人、资产管理员

| 步骤  | 操作     | 角色   | 接口/服务                                         | 数据库变更                                       | 触发条件/校验                                        |
| --- | ------ | ---- | --------------------------------------------- | ------------------------------------------- | ---------------------------------------------- |
| 1   | 提交回收申请 | 普通用户 | `POST /api/v1/recycle-assets/`                | `recycle_asset` 表创建                         | 必须关联有效的 `recycle_outasset`（出库记录编码），且出库状态为 `in_use` |
| 2   | 资产状态更新 | 系统自动 | `RecycleAssetService.create()`                | `asset` 表：`status→recycled_pending`，写入回收仓库 | 事务包裹                                           |
| 3   | 出库记录标记 | 系统自动 | `OutAsset` 表 `return_date` 更新                | 事务内完成                                       |                                                |

**注意**：回收后资产需运营管理员确认仓库位置（可在回收时传入）。

---

### 流程 4：资产报废

**参与角色**：申请人、运营管理员、系统管理员

#### 阶段一：待报废申请

| 步骤  | 操作     | 角色    | 接口/服务                          | 数据库变更                                         | 触发条件/校验                |
| --- | ------ | ----- | ------------------------------ | --------------------------------------------- | ---------------------- |
| 1   | 提交报废申请 | 有权限用户 | `POST /api/v1/damaged-assets/` | `damaged_asset` 表创建                           | 资产生效，且状态不能为 `scrapped` |
| 2   | 资产状态变更 | 系统自动  | `DamagedAssetService.create()` | `asset`：`status→damaged` | 事务内，并生成审计快照            |

#### 阶段二：报废确认（经审批后）

| 步骤  | 操作      | 角色    | 接口/服务                        | 数据库变更                                       | 触发条件/校验     |
| --- | ------- | ----- | ---------------------------- | ------------------------------------------- | ----------- |
| 1   | 确认报废    | 系统管理员 | `POST /api/v1/waste-assets/` | `waste_asset` 表创建                           | 仅待报废状态资产可执行 |
| 2   | 资产变为已报废 | 系统自动  | `WasteAssetService.create()` | `asset`：`status→scrapped`，清空使用信息 | 不可逆操作，永久留存  |

**异常处理**：报废审批未通过时，`damaged_asset` 记录可被驳回，资产状态应回退到 `in_store`（需单独开发驳回接口，Service 显式处理）。

## 4. 流程执行通用规则

- **接口幂等**：所有创建类接口（出库、回收等）必须支持幂等键（Idempotency-Key），防止重复提交创建多条记录。
- **事务安全**：涉及库存数量、资产状态变更的操作，必须在 `@transaction.atomic` 块中完成，任何异常必须回滚所有数据变更。
- **审计留痕**：每一步状态变更和数据修改，必须生成 `DATA_CHANGE` 审计日志（旧值/新值快照），通过信号或 Service 显式调用写入。
- **权限控制**：严格遵循《权限矩阵表》，所有接口需通过 `IsAuthenticated` 和自定义权限类（如 `IsAssetOwnerOrAdmin`）校验。

## 5. 核心接口与数据表映射

| 业务场景    | 接口                             | 主要涉及表                                 | 关键写入                |
| ------- | ------------------------------ | ------------------------------------- | ------------------- |
| 资产创建/入库 | `POST /api/v1/assets/`         | `am_asset`                            | 创建资产记录，自动生成编码       |
| 资产出库    | `POST /api/v1/out-assets/`     | `am_out_asset`, `am_asset`            | 创建出库单，更新资产状态/使用信息   |
| 资产回收    | `POST /api/v1/recycle-assets/` | `am_recycle_asset`, `am_asset`, `am_out_asset` | 创建回收单，资产变为已回收待发放   |
| 待报废     | `POST /api/v1/damaged-assets/` | `am_damaged_asset`, `am_asset`        | 待报废记录，资产标识为待报废      |
| 已报废     | `POST /api/v1/waste-assets/`   | `am_waste_asset`, `am_asset`          | 报废记录，资产终态变更         |
| 未登记资产审批 | `POST /api/v1/unregisteredassets/unregistered-assets/{code}/approve/` | `am_unregistered_asset`, `am_asset`, `am_out_asset` | 根据场景类型创建对应记录（S1/S2/S3） |

> 完整的字段定义和约束请参考《资产数据字典》。

## 6. 开发测试要点

- **状态机测试**：覆盖所有合法流转路径，以及非法跳转（如从 `in_store` 直接到 `scrapped` 应被拒绝）。
- **权限验证**：普通用户不能审核自己提交的申请，不能操作非本部门资产。
- **并发场景**：同一资产同时被两人领用时，后提交的请求应因状态不满足而失败。
- **回滚验证**：模拟 Service 中抛出异常，确保事务回滚后数据库状态与操作前一致。
- **审计日志验证**：每次状态变更后检查 `AssetOperationLog` 是否正确记录了操作前/后数据快照。
